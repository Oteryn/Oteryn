# Publication Integrity Policy

Status: active contract after reviewed integration to protected META `main` and explicit provider adoption.

## Purpose

This contract governs publication of an already-prepared material local Git candidate to its allocated canonical task branch. It prevents a transport or credential failure from silently changing the candidate, rewriting branch history, publishing adjacent repositories/refs, or destroying the only recoverable copy of useful work.

It is not a merge authority, does not replace repository CI/review/Merge Queue, and does not globally forbid repository-native API writes for operations that are not publishing an existing material local candidate.

## Exact-candidate invariant

Once a material local commit is selected as the publication candidate, publication must preserve that exact commit identity. The publication operation must not reconstruct the candidate from files, patches, prose, test output, or manually assembled Git objects.

Before mutation, bind and verify:

- repository plus exactly one configured, credential-free approved push target that uses the canonical lowercase spelling of a fixed native push-capable URL scheme (`ssh`, `git`, `http`, `https`, or `file`) or a native local/scp-like form, and does not use explicit Git remote-helper `<transport>::<address>` syntax;
- for a local filesystem or supported local `file://` push target, reject unsupported URL authorities and literal query/fragment delimiters, bind the resolved non-symlink endpoint, its actual Git administrative directory, and the effective common Git directory used for refs and objects before mutation, route both preflight and post-push readback through a stable open handle to that common directory inherited by `ls-remote`, revalidate every identity after readback, and hold Git's exclusive branch-ref lock from before observation through classification; for packed-only branches, securely create missing loose-ref parent directories beneath the bound common Git directory using no-follow directory handles, without traversing a symlink or redirect; every loose symbolic-ref header beginning with `ref:` is rejected because the named lock does not protect its referent, and a missing, replaced, symlinked, redirected, or recreated linked-worktree `commondir`, a replaced `.git` entry, an unavailable/already-held branch lock, or any otherwise unstable target must not supply `ALREADY_PUBLISHED` or `PUBLISHED` evidence;
- the approved push target is not also a configured Git remote name whose alias resolution could redirect the repository operand;
- the approved push target is not resolvable through Git's legacy `$GIT_DIR/remotes/<name>` or `$GIT_DIR/branches/<name>` repository aliases, including alias files reached through symlinks;
- no effective Git `url.*.insteadOf` or `url.*.pushInsteadOf` rewrite rule, so the approved endpoint cannot be redirected after validation;
- no repository-local or worktree-local `credential.*.helper` configuration, including helpers introduced through an active local include; transport credentials must come from an authorized system/global/environment path rather than repository-controlled executable configuration;
- no repository-local or worktree-local executable transport command (`core.sshCommand`, `core.gitProxy`, or `core.askPass`), including values introduced through an active local include; authorized system/global/environment transport configuration remains outside repository control;
- no repository-local or worktree-local `core.alternateRefsCommand`, including values introduced through an active local include; it is repository-controlled executable configuration that Git may invoke while enumerating alternate history;
- no repository-local or worktree-local HTTP routing or TLS-trust overrides, including URL-scoped `http.*` forms, `http.proxy`, `http.curloptResolve`, `http.extraHeader`, certificate-verification/CA settings, HTTPS-proxy trust settings, or `remote.<selected>.proxy`; authorized system/global HTTP configuration remains outside repository control;
- no executable `filter.<driver>.clean` or `filter.<driver>.process` configuration for a filter value reported by Git for any tracked path in the publication workspace, including literal values that spell `unspecified`, `unset`, or `set`;
- configured `push.pushOption` values must be neutralized at command scope so the authorized branch update cannot implicitly request server-side actions;
- all Git objects required to validate ancestry, inspect the candidate, create/verify recovery, and publish/read back the candidate must already exist locally; lazy promisor fetching is disabled and a missing required object is a publication blocker;
- no Git replacement refs, graft metadata, or replacement-ref namespace override; ancestry must be evaluated against the unmodified object graph;
- canonical task branch, bound locally and in recovery artifacts by its fully qualified `refs/heads/<branch>` identity so a colliding short tag cannot alter branch selection;
- exact candidate commit SHA;
- exact expected current remote branch SHA;
- checked-out local branch/head when a local Git workspace is used;
- all repository-wide safety scans are anchored at the actual top-level Git worktree even if the caller supplies a nested `--cwd`;
- no tracked `skip-worktree` or `assume-unchanged` index flags that could hide local bytes from the clean-worktree probe;
- tracked gitlinks must not have a populated/initialized submodule worktree in the publisher workspace;
- a clean isolated worktree, so the recovery artifact contains all intended work;
- the expected remote SHA is an ancestor of the candidate, so the update is fast-forward.

A separately authorized normal merge-up may create a new candidate before this freeze. It does not authorize rewriting the frozen candidate during publication.

## Recovery preservation

Before the first publication attempt, create a verified recovery artifact for a material unpublished candidate when the execution environment can be disposed, lost, or handed off. The artifact must preserve the exact Git objects needed to recover the candidate and must advertise that exact candidate head. Record its digest and any prerequisite commit required for incremental recovery.

`git bundle` is the preferred Git-native representation. A bundle stored only inside the disposable worktree is insufficient. The caller/executor remains responsible for placing the verified artifact on an authorized durable surface before it treats workspace disposal or custody release as safe. Recovery creation must not demand-fetch missing objects from a promisor remote: the publisher runs Git with `GIT_NO_LAZY_FETCH=1`, so any required object absent from local storage fails closed before publication instead of executing repository-controlled promisor transport.

A patch, prose summary, file list, diff excerpt, or test log is evidence but is not an exact-candidate recovery substitute. Submodule-local work is separate repository work and is never implicitly published or treated as part of the superproject recovery artifact.

## Publication route

For a local Git candidate, the selected route is a single Git ref update of the exact candidate to the canonical task branch followed by live remote-head readback. `tools/governance/publication_integrity.py` implements the deterministic local guard and transport wrapper when a Git workspace is available. The helper first resolves any supplied working directory to `git rev-parse --show-toplevel`; a nested invocation must therefore receive the same repository-wide filter/index/gitlink checks as an invocation from the repository root. Every Git subprocess launched by the helper preserves the caller environment while forcing `GIT_NO_LAZY_FETCH=1`, covering safety scans, ancestry, recovery bundle creation/verification, mutation, and readback.

The selected remote must resolve to exactly one configured push URL and that URL must equal the approved publication target. Explicit Git remote-helper endpoints using `<transport>::<address>` and implicit helpers selected by unknown/custom or mixed-case `scheme://` URLs are rejected before Git execution; the helper never discovers helpers from `PATH` or recursively executes or resolves them. URL schemes must use the canonical lowercase spelling of the native push-capable `ssh`, `git`, `http`, `https`, and `file` set, because Git can dispatch an exact-case `git-remote-<scheme>` helper for a mixed-case spelling. Native local filesystem paths and scp-like SSH forms remain supported; `ftp` and `ftps` are not publisher transports. Effective Git URL rewrite rules are rejected rather than reimplemented or partially interpreted. An endpoint string that is itself another configured remote name is rejected rather than left to Git's remote-name/URL ambiguity. The same rejection applies when `git remote get-url` can resolve the endpoint through legacy `$GIT_DIR/remotes/<name>` / `$GIT_DIR/branches/<name>` metadata even though `git remote` does not list that alias. Repository/worktree credential helpers, executable transport commands, `core.alternateRefsCommand`, and HTTP routing/TLS-trust overrides are rejected before remote readback and rechecked before mutation, including values loaded through local includes, so repository-controlled credential, SSH, git-proxy, askpass, alternate-ref enumeration, proxy, DNS, header routing, or weakened/replaced certificate trust cannot execute or redirect publication before recovery preservation or during the guarded push. The alternate-ref fence is also applied before recovery creation because `git bundle create` may enumerate alternate refs. Authorized system/global credential helpers, transport commands, alternate-ref commands, HTTP configuration, or environment-backed authentication remain compatible because they are outside repository/worktree control. Preflight readback, mutation and post-mutation readback all use the same resolved push endpoint; a distinct fetch URL is not publication evidence, multiple push URLs fail closed before mutation, and no `insteadOf`/`pushInsteadOf` chain may redirect the endpoint. For local filesystem and local `file://` endpoints, unsupported `file://` authorities are rejected because Git may ignore the authority and use the local path. Literal `?` and `#` delimiters are also rejected because Git treats them as filesystem path content while generic URL parsing can strip their suffixes and bind a different repository. The helper binds the resolved target, its Git administrative directory, and its effective common Git directory by filesystem device/inode identity before the guarded push. For linked worktrees, the `commondir` indirection file must exist as a stable non-symlink and resolve to the bound common directory. Local preflight and post-push `ls-remote` use a stable open handle to that common directory, where refs and objects live, and the endpoint, administrative directory, `commondir` file, and common directory are all checked again after readback. Before observing the branch, the helper exclusively creates the branch's normal `.lock` file through non-symlink directory handles, securely creating any absent loose-ref parents required by a packed-only branch relative to already-open parents and revalidating that hierarchy before classification. It never follows a symlink or redirected component while opening or creating the hierarchy. The helper rejects any loose named branch whose content begins with the symbolic-ref syntax marker `ref:` and retains the ref lock until classification completes. Symbolic target branches fail closed because their referents remain independently mutable under the named lock. If the hierarchy is unsafe, the lock is unavailable, or another writer already owns it, the read fails closed. Consequently, a Git writer cannot hold the candidate through every read and restore the predecessor between the final observation and the `ALREADY_PUBLISHED` or `PUBLISHED` decision. This fence applies uniformly to bare, ordinary non-bare, and linked-worktree local endpoints, including nested branches stored only in `packed-refs`. A path, ref hierarchy, or `commondir` replaced at any readback boundary, an unavailable stable handle or branch lock, a symlink, a renamed/recreated repository, or any other local target identity change is classified as ambiguous after mutation and cannot be accepted as `PUBLISHED` evidence even if the replacement repository already contains the candidate.

Candidate ancestry is checked with replacement objects disabled after replacement refs and graft metadata are rejected. The helper uses an explicit expected-old-value `--force-with-lease=<ref>:<expected_sha>` only as compare-and-swap protection against movement between preflight and mutation. It independently requires `expected_sha` to be an ancestor of the exact candidate before the push. Therefore the authorized update remains fast-forward; the lease does **not** authorize a non-fast-forward update, history rewrite, reset, rebase, or ordinary force-push.

The checked-out branch is compared as its full symbolic `refs/heads/<branch>` ref. Candidate resolution and recovery bundle creation use that same fully qualified branch ref, and bundle verification requires the advertised candidate under exactly that ref name; unqualified revision lookup is not permitted to let a colliding tag select or obscure publication state.

The clean-worktree probe enumerates tracked paths and resolves attributes with `git check-attr --all` without converting file contents. A path with no effective filter attribute produces no `filter` record, while every reported `filter` value is treated as a possible driver name, including reserved-looking strings such as `unspecified`, `unset`, and `set`. If the corresponding `filter.<value>.clean` or `filter.<value>.process` command exists, publication fails closed before `git status`; this avoids conflating Git's state words with literal driver names. Unrelated executable filter configuration remains allowed when no tracked path reports that driver, such as an unused Git LFS driver. The probe also rejects tracked `skip-worktree` and `assume-unchanged` index flags. It requires tracked submodule worktrees to be deinitialized/empty, then runs top-level `git status` with `--ignore-submodules=all`, optional index locking disabled, `core.fsmonitor=false`, and `core.hooksPath` pointed at a fresh trusted empty directory. This prevents repository-controlled active filters, submodule-local filters, fsmonitor or index hooks from executing code or publishing elsewhere during the safety check.

The guarded push applies `-c push.pushOption=` at command scope and uses `--no-verify`, `--recurse-submodules=no`, `--no-follow-tags` and `--no-signed`. Clearing `push.pushOption` prevents repository, worktree, global, or system configuration from silently transmitting server-specific push options such as deployment instructions. The remaining fences ensure repository-local `pre-push` hooks cannot run, configured recursive-submodule publication cannot widen the operation to another repository, `push.followTags=true` cannot add tag refs, and `push.gpgSign` cannot invoke a repository-configured `gpg.program` or add signed-push side effects. The only intended ref update is the exact candidate to the canonical task branch guarded by the expected-old-value lease.

If the normal Git publication path is unavailable, do not use ad-hoc Git Data API blob/tree/commit/ref construction, per-file Contents API reconstruction, reset, rebase, non-fast-forward push, or manual ref replacement to synthesize a remote substitute for the existing candidate. Preserve the candidate/recovery artifact and classify the lane as blocked by the exact observed publication capability failure. If required candidate objects are missing locally, hydrate them only through a separately authorized trusted preparation step before entering publication; the publication helper itself must not lazily fetch them.

This restriction is candidate-specific. It does not prohibit an independently authorized API-native edit whose intended operation is itself the API write and which is not pretending to publish an already-prepared local commit.

## Ambiguous outcomes

A nonzero push exit, timeout, interrupted client, or lost response is an ambiguous transport result, not proof that the server rejected the mutation. Before retrying or attempting recovery, revalidate the same approved push endpoint and then read the live canonical branch through that endpoint. For a local filesystem endpoint, the readback is admissible only if the path is still a non-symlink and its bound resolved path/device/inode identity is unchanged from immediately before the push:

- remote head equals candidate: publication succeeded; continue from that exact remote candidate;
- remote head equals expected predecessor: publication was not applied; retain recovery and diagnose the exact capability failure before another attempt;
- remote head is a third SHA: stop with remote-head drift and reconcile writer/ownership/live state before mutation;
- endpoint identity changed, became a symlink, or remote head cannot be read: remain blocked with an ambiguous outcome; do not retry or rewrite the ref blindly.

No automatic force update, rollback, no-op commit, replacement commit, or destructive cleanup is permitted as ambiguity recovery.

## Completion boundary

A verified recovery artifact protects work from loss but does not make local work delivered. Repository lifecycle evidence begins only when the intended exact candidate is durably present on the approved GitHub branch/PR. Readiness, review and integration continue to use the repository's existing exact-head gates and protected Merge Queue path.
