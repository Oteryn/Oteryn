# Restricted publishing-credential compatibility

Load this procedure when an already-authorized GitHub publication needs CLI/Git credential compatibility. Ordinary API-backed documentation work that is not publishing an existing material local candidate does not require it.

This profile applies only after the repository lifecycle has allocated an approved task branch and existing PR. It does not grant PR-write permission to a restricted publishing credential; PR creation remains a separately authorized control-plane action.

## Existing local candidate publication

Once a material local candidate commit exists and is the intended payload for an allocated task branch, publication MUST preserve that exact candidate commit. The normal route is a fast-forward Git publication of that commit to exactly one approved configured push target after verifying the live head at that push endpoint is the expected predecessor and that the expected predecessor is an ancestor of the candidate on the unmodified Git object graph. A separately authorized normal merge-up is compatible with this rule because it produces the candidate before publication; publication itself must not rewrite that candidate.

Use `tools/governance/publication_integrity.py` when an isolated Git workspace is available. Any supplied `--cwd`, including `.`, is first normalized through `git rev-parse --show-toplevel`, so all filter/index/gitlink safety scans cover the complete worktree rather than only the caller's path prefix. The helper requires the selected remote to resolve to exactly one credential-free configured push URL matching the approved target; permits only the canonical lowercase spellings `ssh`, `git`, `http`, `https`, and `file` for native push-capable URL schemes while retaining native local filesystem paths and scp-like SSH forms; rejects `ftp`, `ftps`, unknown/custom or mixed-case `scheme://` URLs and explicit Git remote-helper `<transport>::<address>` endpoints before Git execution rather than discovering or invoking exact-case `git-remote-*` helpers from `PATH`; rejects an endpoint that is itself another configured remote name or is resolvable through legacy `$GIT_DIR/remotes/<name>` / `$GIT_DIR/branches/<name>` metadata; rejects effective `url.*.insteadOf` / `url.*.pushInsteadOf` rules; rejects repository-local and worktree-local `credential.*.helper`, `core.sshCommand`, `core.gitProxy`, `core.askPass`, and `core.alternateRefsCommand` entries including values loaded through local includes; rejects repository-local and worktree-local HTTP proxy, DNS/header routing and TLS-trust overrides, including URL-scoped forms and `remote.<selected>.proxy`, while retaining system/global compatibility; resolves tracked attributes with `git check-attr --all` and rejects executable `clean` / `process` configuration for every reported `filter` value, including literal `unspecified`, `unset`, or `set`; rejects replacement refs, graft metadata and replacement-ref namespace overrides; rejects tracked `skip-worktree` / `assume-unchanged` flags; and requires tracked gitlink worktrees to be deinitialized/empty before the clean probe. Legacy aliases are checked through Git's own local `remote get-url` resolver before any endpoint readback or push, so regular alias files and symlinked alias entries cannot redirect a relative approved endpoint. For a local filesystem or supported local `file://` endpoint, the helper rejects unsupported authorities and literal query/fragment delimiters, then binds the resolved endpoint, its actual non-symlink Git administrative directory, and its effective common Git directory before preflight. Local preflight is routed through that exact original identity rather than independently trusting a replacement endpoint. The helper repeats the binding after recovery creation and requires the mutation-time identity to equal the approved non-linked identity. Linked-worktree local publication targets fail closed at both bindings because a descriptor for the per-worktree administrative directory cannot stop `receive-pack` from re-reading a mutable `commondir`; bare and ordinary non-bare local targets remain supported. The guarded push uses the already-open verified Git-directory descriptor as its repository operand and retains the Git/common-directory handles through readback. Preflight and post-push local readback use an open handle to the common Git directory inherited by `ls-remote`, then check the endpoint, administrative directory, `commondir` file, and common directory identities again. Before reading the branch, the helper acquires Git's exclusive per-ref `.lock` through non-symlink directory handles. If a packed-only nested branch has no loose-ref parents, the helper creates each missing directory relative to its already-open verified parent, opens it with no-follow semantics, and revalidates the complete hierarchy before classification; a symlinked, redirected, or replaced component fails closed. The helper keeps the exact loose-ref object open and re-reads its complete contents and pathname identity before and after classification; when no loose ref exists, it applies the same content-and-identity rule to the exact open `packed-refs` object instead of resolving the ref again from the mutable root pathname, and it revalidates through the already-open no-follow parent that the absent loose ref has not been restored through or after classification. It rejects every loose symbolic-ref header beginning with `ref:` whose referent would remain independently mutable and retains the lock through classification. An unavailable or already-held lock fails closed, and a supported Git writer cannot restore the predecessor after the final observation but before `ALREADY_PUBLISHED` or `PUBLISHED` is decided. This applies to packed or loose branches in bare and ordinary non-bare local endpoints; linked-worktree readback remains fenced, but mutation is rejected. Replacement of the endpoint, `.git`, `commondir`, loose- or packed-ref storage, or ref hierarchy at the readback/classification boundary, inability to retain the stable common-directory handle or branch lock, symlink substitution, rename/recreation, or any other target identity change makes the post-mutation outcome ambiguous and prevents unstable evidence from supplying publication success. The alternate-ref command fence is reached before recovery creation because `git bundle create` may enumerate alternate refs. The top-level clean check ignores submodule contents, disables optional index writes/fsmonitor and binds `core.hooksPath` to a fresh trusted empty directory so repository-controlled filters, submodule-local filters, fsmonitor or index hooks cannot side-publish.

Every Git subprocess launched by the helper preserves the caller environment while forcing `GIT_NO_LAZY_FETCH=1`. This applies to safety scans, revision/ancestry checks, recovery bundle creation/verification/list-heads, guarded push, and remote readback. A partial clone or promisor-configured repository therefore cannot demand-fetch a missing object during publication; if a required object is not already local, publication fails closed before the approved branch update rather than invoking a repository-controlled promisor transport. Hydrate missing objects only in a separately authorized trusted preparation step before entering publication.

Using `check-attr --all` is intentional: paths with no effective filter attribute emit no `filter` record, while any value Git does report is treated as a possible literal driver. This fails closed around Git's state/value text overlap instead of dropping reserved-looking driver names such as `unspecified` or `unset` before `git status` can execute their configured filter commands.

Before the first network readback, repository/worktree credential helpers, executable transport commands, `core.alternateRefsCommand`, HTTP routing/TLS-trust overrides, and modern/legacy repository-operand alias collisions are rejected so repository-controlled credential, SSH, git-proxy, askpass, alternate-ref enumeration, or alias routing cannot execute or redirect publication before the recovery bundle exists. System/global credential helpers, system/global transport/alternate-ref commands and environment-backed authentication remain allowed as the authorized host path. These repository/worktree fences are rechecked immediately before the guarded push. Local branch identity is compared as the full symbolic `refs/heads/<branch>` ref, and candidate resolution, bundle creation and advertised-head verification use exactly that qualified ref so a same-named tag cannot affect recovery or publication selection. Before mutation the helper creates and verifies a recoverable Git bundle outside the disposable worktree, with the alternate-ref command fence applied before bundle creation. It performs one exact-candidate branch update guarded by an expected-old-value lease, clears configured server push options at command scope with `-c push.pushOption=`, bypasses `pre-push` hooks, explicitly disables recursive submodule publication, automatic follow-tags and signed-push behavior, and revalidates the approved endpoint before reading the branch back. For local filesystem targets, that revalidation includes the physical filesystem identity bound immediately before push; a changed or symlinked target is treated as ambiguous and no readback from it is trusted.

A separate fetch URL is not publication evidence, multiple push URLs fail closed before mutation, modern or legacy remote-alias collisions are publication blockers, Git URL rewrites are publication blockers until removed from the effective configuration, repository/worktree credential helpers and executable transport commands are publication blockers until removed from those scopes, active executable clean/process filters are publication blockers while reported for tracked paths, missing local objects are publication blockers while lazy promisor fetch remains disabled, replacement/graft history cannot authorize ancestry, hidden index flags cannot suppress local recovery state, a local filesystem target must retain its bound non-symlink identity across mutation/readback, and an initialized submodule worktree must be handled separately rather than implicitly traversed by the superproject publisher. Unused global filter configuration does not block publication merely because it exists. Running the helper from a nested directory does not narrow any of these checks.

The helper's explicit `--force-with-lease=<ref>:<expected_sha>` is used only as compare-and-swap protection for the expected predecessor. Candidate ancestry is checked independently first with replacement objects disabled, so this does not authorize a non-fast-forward update or history rewrite. `-c push.pushOption=` neutralizes configured `push.pushOption` values so the branch update cannot carry deployment or other server-specific instructions, `--recurse-submodules=no` ensures `push.recurseSubmodules` cannot widen the operation to another repository, `--no-follow-tags` ensures `push.followTags=true` cannot add tag refs, and `--no-signed` ensures `push.gpgSign` cannot invoke a configured `gpg.program` during the guarded update. An agent must not weaken these command-line fences or treat the lease as a general force-push exception.

If the normal Git publication path is unavailable, do **not** use per-file Contents API commits, multiple candidate commits, force/ref replacement, reset, rebase, non-fast-forward push, or mixed partial reconstruction. A separately authorized API-native authoring route may select a **new** candidate through the preferred atomic expected-head primitive (for example `createCommitOnBranch(expectedHeadOid=...)`) or, when that primitive is unavailable, through the bounded connector-compatible Git Data route: verify a fresh explicit single-writer allocation for the exact canonical task branch; live-read and require the expected predecessor immediately before mutation; create exactly one Git Data commit whose sole parent is that predecessor and whose tree contains the complete bounded delta; perform exactly one non-force (`force=false`) update of only that branch; immediately live-read and require the candidate head. Git-refs `force=false` is not an atomic expected-head compare-and-swap; the narrow residual race is accepted only inside that one-writer task-branch model and the route is forbidden for protected `main`, Merge Queue refs, shared branches or uncertain ownership. Pre-readback drift, failed/timed-out mutation or any third SHA fails closed before retry. Candidate-specific validation/review evidence from any superseded local commit is not reusable.

## Ambiguous publication outcome

A failed, interrupted, timed-out, or otherwise ambiguous push is not evidence that GitHub rejected the candidate. Revalidate the same approved push endpoint before any retry or recovery action and only then read the live canonical branch. For a local filesystem endpoint, the target path must still be non-symlinked and must retain the same bound resolved path/device/inode identity from immediately before the push:

- if the remote head equals the exact candidate, publication succeeded despite the ambiguous transport result;
- if the remote head still equals the expected predecessor, retain the candidate and recovery artifact and report the exact publication capability failure;
- if the remote head is any third SHA, stop with remote-head drift and reconcile ownership/state before another mutation;
- if the local endpoint identity changed, became a symlink, or cannot be read safely, retain the verified recovery artifact and classify the outcome as ambiguous rather than accepting evidence from the replacement target.

Do not retry an ambiguous push until that revalidation/readback has classified the remote state. Never use a force update as automatic cleanup.

## Recovery preservation

Before releasing or disposing of a writer/workspace that contains a material unpublished candidate, preserve a recovery artifact containing the exact Git objects required to recover that candidate. A Git bundle is preferred when Git is available. The artifact is evidence only after verification proves that it advertises the exact candidate head and records any prerequisite commit required for incremental recovery. A patch, prose summary, test log, or remembered edit is not an exact-candidate recovery substitute. Local submodule work is separate repository work and must not be assumed to be preserved by the superproject bundle. Recovery creation is local-object-only under `GIT_NO_LAZY_FETCH=1`; a missing object must be repaired before publication rather than lazily retrieved during recovery creation.

Recovery preservation does not make local-only work delivered. The approved GitHub branch/PR remains lifecycle authority, and exact-head CI/review starts only after the intended candidate is durably present there.

## Credential compatibility

For an authorized write to that branch/PR, when `GH_TOKEN` and `GITHUB_TOKEN` are unset but agent-visible `GH` is present, it may be passed transiently as `GH_TOKEN="$GH"` to the exact authorized `gh` command. Environment mapping alone does not authenticate `git push`: verify that the existing system/global/environment credential and transport path can consume the authorized identity without exposing or persisting it. Repository/worktree `credential.helper`, `core.sshCommand`, `core.gitProxy` and `core.askPass` configuration is intentionally not accepted by the exact-candidate publisher because it is repository-controlled executable configuration. If the normal Git publication path is unavailable, prefer an authorized atomic expected-head API candidate-creation primitive when exposed; otherwise the bounded connector-compatible Git Data route above may be used only with its exact single-writer, immediate predecessor-readback, one-commit, one non-force ref-update and immediate candidate-readback conditions. If neither authorized API mode is available, preserve the candidate/recovery artifact and report the exact limitation rather than inventing another publication route. Credential compatibility does not broaden either API route.

Never embed the token in a remote URL or persist a new repository/worktree credential/transport helper to bypass that boundary. Credential presence expands no repository/path/task/merge/production permission. Do not perform a non-fast-forward update; verify the remote exact head after publishing.
